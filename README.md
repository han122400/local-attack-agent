# Local Attack Agent

로컬 Ollama 또는 OpenRouter API 모델이 OWASP Juice Shop의 화면과 네트워크 관찰을 바탕으로 탐색 계획과 다음 행동을 선택하는 실험 프로젝트입니다. FastAPI 대시보드에서 계획, 모델 출력, 관찰 기록, 가설과 응답 비교 결과를 확인할 수 있습니다.

기본 대상은 `http://127.0.0.1:3000/`의 Juice Shop입니다. 새 실험 화면에서 본인이 소유하거나 탐색 권한이 있는 사이트의 HTTP(S) URL을 직접 입력하고, 설정 저장 버튼으로 다음 방문에도 유지할 수 있습니다. 각 실험의 Playwright 페이지 요청과 기본 HTTP 도우미는 선택한 대상의 origin으로 제한됩니다. Juice Shop이 아닌 대상은 연결을 선확인하거나 자동 초기화하지 않습니다. 응답 차이는 관찰 결과로 기록하며 취약점 확정을 의미하지 않습니다.
브라우저는 같은 origin의 일반 HTTP 메서드(GET·HEAD·OPTIONS·POST·PUT·PATCH·DELETE)를 허용하고
WebSocket 연결과 외부 origin 요청은 차단합니다. 상태 변경은 사용자가 허용한 목표·범위를 따라야 합니다. 실행은 최대 10분이며,
응답 본문 수집은 최대 8초입니다. 수집 실패 응답은 오류로 기록하고 실험 후보에서 제외합니다.
브라우저 리다이렉트에도 origin 제한을 적용하도록 Chromium 네트워크 규칙을 설정합니다.
범위 검사를 설정할 수 없는 브라우저에서는 요청을 보내지 않고 하네스 차단 사유를 남깁니다.

## 실행 환경

- Python 3.10 이상
- Docker Desktop
- Ollama 및 설치된 로컬 모델 또는 OpenRouter API 키
- Playwright Chromium

## 시작하기

프로젝트 폴더에서 Python 의존성과 브라우저를 설치합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
```

macOS/Linux에서는 다음 명령을 사용합니다.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m playwright install chromium
```

Juice Shop 실습 컨테이너를 준비합니다.

```powershell
docker pull bkimminich/juice-shop:v20.2.0
docker run -d --name juice-lab -p 127.0.0.1:3000:3000 bkimminich/juice-shop:v20.2.0
```

컨테이너가 이미 있다면 `docker start juice-lab`으로 시작합니다. Ollama를 실행하고 `ollama list`에 모델이 있는지 확인한 뒤 대시보드를 시작합니다.

```powershell
.\.venv\Scripts\python.exe app.py
```

macOS/Linux에서는 `.venv/bin/python app.py`로 시작합니다.

테스트는 Windows에서 `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`,
macOS/Linux에서 `.venv/bin/python -m unittest discover -s tests -v`로 실행합니다.
브라우저 테스트에는 위에서 설치한 Chromium이 필요하며, 모델 응답과 사이트는 모의 데이터로 검증합니다.

브라우저에서 <http://127.0.0.1:8765/>에 접속해 설치된 모델을 선택합니다. Ollama 연결 주소는 `http://127.0.0.1:11434`입니다.

### OpenRouter 모델 사용

프로젝트 루트의 `.env`에 키를 직접 입력합니다. 형식은 `.env.example`을 참고하세요.

```dotenv
OPENROUTER_API_KEY=여기에_발급받은_키
```

의존성을 설치한 뒤 서버를 재시작하고, 새 실험 화면에서 **모델 제공자 → OpenRouter API**를 선택합니다.
API에서 조회한 텍스트 생성 모델 중 하나를 선택해 실행할 수 있습니다. Ollama를 실행하지 않아도 됩니다.
키를 수정한 경우 모델 목록의 **새로고침**을 누르면 다시 읽습니다. 같은 이름의 프로세스 환경변수가 있으면 `.env`보다 우선합니다.

목표, 관찰 내용, 코드와 실행 결과가 OpenRouter 및 해당 모델 제공자에게 전송되며 모델별 요금이 적용됩니다.
키는 서버의 인증 헤더에만 넣고 API 응답·세션 로그·하위 실행 프로세스 환경에는 넣지 않습니다. `.env`는 Git에서 제외됩니다.

Thinking과 Temperature는 모델이 지원할 때만 적용합니다. 컨텍스트 토큰은 앱의 대화 압축 예산이며
원격 모델의 컨텍스트 크기를 변경하지 않습니다. 출력 토큰은 `max_tokens`로 전달하되,
모델의 한도와 입력 분량 추정치에 따라 상한을 줄입니다. 토크나이저별 실제 입력 한도는 제공자가 최종 검증합니다.
구조화 출력을 지원하는 모델에는 JSON Schema를, JSON 모드만 지원하면 JSON 모드를 요청하며,
그 외 모델도 기존 프롬프트와 명령 검증·재시도 흐름을 사용합니다.
인증 실패, 크레딧 부족, 호출 제한은 화면과 로그에 오류로 표시하며 다른 모델로 자동 전환하지 않습니다.

### 호출 예산과 종료 보고

모델 호출 한도는 기본 40회이며 화면에서 변경한 값을 사용합니다. 모든 프롬프트 버전에서 설정한
호출 예산의 **마지막 1회**를 보고에 예약합니다(50회면 50번째, 60회면 60번째 호출).
탐색 재시도도 예약분을 소비하지 못하며, 보고 호출의 탐색 명령은 실행하지 않습니다. 한도가 1회면 보고만 합니다.
마지막 보고가 실패하면 추가 호출 없이 저장된 관찰로 보고서를 만듭니다. 시간·도구 예산이 먼저 부족하면
더 일찍 보고하며, 모델이 충분한 결과를 얻었을 때도 조기 종료할 수 있습니다.

### HTTP 도우미와 요청 재사용

- 기존 `http_get`은 상태·헤더·본문 미리보기와 `body_truncated`·`binary`를 반환합니다. 본문은 최대
  2,000자(J2 실행은 2,000,000자)이며, 더 긴 전체 텍스트가 필요하면 `get_text`를 사용합니다. 바이너리를 텍스트로 해석하지 않고,
  쿠키 헤더는 값을 가리고 속성을 남깁니다. 별도의 자동 HTTP 응답 수집기나 전체 응답 저장은 추가하지 않았습니다.
- 브라우저가 실제 전송한 최근 폼 요청 8개를 실행 중 메모리에 보관합니다. `captured_requests()`로
  요청 ID와 필드명을 확인하고 `await replay_request(id, fields={"필드명": "새 값"})`로 재사용합니다.
  숨김 필드·본문 형식·프레임워크 헤더를 유지하고 현재 브라우저 쿠키를 사용합니다. 캡처한 인증 헤더는
  보존하므로 실제 신원과 토큰 유효성을 확인해야 합니다. 캡처는 요청 성공이나 취약점의 증거가 아닙니다.
  URL 인코딩·JSON·multipart에서 지정하지 않은 필드의 원문을 유지하며, 워커가 재시작되면 이전 요청 ID는 만료됩니다.
- 재사용은 요청을 다시 전송합니다. 허가된 범위에서만 사용하며, 만료된 토큰은 새 요청을 관찰해 갱신합니다.
  2 MB 초과 본문·파일 내용 변경은 지원하지 않습니다. 요청 본문·쿠키·인증값은 요청 목록에 노출하지 않습니다.
- `blocked_requests`에는 하네스의 차단 이유를 남깁니다. 이를 사이트 오류로 해석하지 않습니다.
  실패·타임아웃·중단 이전에 얻은 출력은 부분 관찰로 보존하며, 전체 실행 성공이나 보안 검증 완료로 계산하지 않습니다.

## 구성

### 시스템 프롬프트 J2.5

서버를 재시작한 뒤 **시스템 프롬프트 → J2.5**를 선택합니다. 로컬 Ollama 모델은 관찰된 참조에서
다음 페이지·스크립트·입력과 비교값을 선택하며, 브라우저 조작과 비교 코드는 실행기가 제공합니다.
모델이 Python이나 셸 명령을 작성하지 않습니다. 기본 프롬프트 선택과 기존 J2는 그대로 사용할 수 있습니다.

- 시작 페이지를 관찰하고 같은 origin의 링크·SPA 경로·스크립트·입력 선언을 기록합니다. 모델이 선택한
  스크립트의 텍스트 분석과 GET 입력의 정상→시험→정상 비교도 고정 코드가 수행합니다.
- 실제 브라우저가 보낸 GET의 쿼리와 인증 헤더는 워커 메모리에만 보관하고, 모델에는 경로와 필드명만
  제공합니다. 워커가 재시작되거나 보관 한도를 넘으면 이전 요청 참조는 만료됩니다. 단일 입력 GET의
  정적 선언은 별도 기준으로 시험할 수 있지만 실제 화면에서 처리됐다는 뜻은 아닙니다.
- 허용 범위를 명시한 격리·복구 가능한 시험에서는 관찰된 POST 요청의 정상→시험→재확인,
  별도 시험 신원 선택과 페이지 접근 차이 검증을 사용할 수 있습니다. 화면 입력은 실제로 보이는
  필드에만 적용되고, 브라우저 입력 검증의 실행 표식은 고정 코드가 만듭니다. 업로드와 임의 버튼
  클릭은 지원하지 않습니다. GET도 대상에 따라 상태를 바꿀 수 있으므로 허가된 목표에서만 실행합니다.
- 각 관찰과 비교는 출처·실행 ID에 연결됩니다. 실패·중단·본문 잘림·불안정한 기준 응답은 미완료로
  남기며, 응답 상태·본문 해시 차이는 취약점 확인이 아닙니다. 비교 보고에는 모델이 선택한 입력값과
  상태·길이·해시를 보관하며 응답 본문은 보관하지 않습니다. 캡처한 요청의 쿼리값은 새 기록에 넣지 않습니다.
- 같은 참조의 같은 행동이 같은 오류로 두 번 연속 실패하면 세 번째 실행을 막고 다른 행동이나 보고를
  요청합니다. 다른 행동을 실행한 뒤에는 재시도할 수 있으며, 거절 횟수와 실패 기록을 남깁니다.
- 모델에는 목표와의 단어 일치, 지원 여부, 최근 실행과 출처를 기준으로 우선 정렬한 참조를 제한해서
  전달합니다. Socket.IO 전송용 입력은 뒤로 미루고, 이미 관찰한 페이지는 후보에서 제외합니다.
  모델에 보여주지 않은 참조도 전체 실행 기록에 남으며, `context_omitted`는 표시에서 빠진 수입니다.
- 목표 상태는 모델의 미검증 판단(`completed`, `partial`, `unknown`)이고, 발견된 참조의 조사 범위는
  별도로 표시합니다. 관찰된 참조가 전부 처리됐다는 의미일 뿐 전체 사이트의 검증 완료는 아닙니다.
  미검토 참조·실패 등이 있으면 기존 `run_result`는 계속 `incomplete`로 남습니다.
- 시험 범위에 등록한 비공개 표식이 기준선·시험·재확인과 유형별 대조를 통과할 때만 검증된 고유
  사례로 기록합니다. 같은 표면의 반복 시험은 한 건으로 합치고, 응답 해시·표식 이름·실행 ID를
  안전한 증거로 남깁니다. 이전 J2.5 기록에는 없는 검증 건수를 추정하지 않습니다. 일반 대상의
  전체 취약점 수를 모르면 비율은 측정 불가로 표시합니다.
- 모델 호출 수(재시도 포함), 판단 소요 시간(재시도와 대기 포함), 첫 정상 비교 단계와 반복 차단 횟수를
  실행 기록 및 스코어에 남깁니다. 과거 실행에 이 수치가 없다면 새로 추정하지 않습니다.
- 시작 관찰도 도구 예산 1회를 사용하고, 한 번의 비교는 도구 1회와 최대 세 요청을 사용합니다.
  보고의 요청 수는 실행 단계 중 기록한 시도로, 단계 사이의 백그라운드 요청이나 일부 리다이렉트는
  누락될 수 있습니다. 마지막 모델 호출은 보고에 예약하며 모델 보고가 실패해도 코드가 관찰과 한계를 보고합니다.

`python benchmarks/j25_replay.py`는 J2와 J2.5의 미리 작성된 모의 결정 형식만 재생합니다.
실제 모델·브라우저·HTTP 실행이나 취약점 발견 성능 비교는 아닙니다.

실제 로컬 모델·브라우저 평가는 `.venv/bin/python -m benchmarks.run_j25_fixture --model qwen3:4b-instruct --repeats 3 --seconds 360`으로 실행합니다.
`benchmarks/j25_fixture_manifest.json`에는 개발용 20건과 별도 최종 평가용 10건, 정상 대조 경로 4개가 등록되어 있습니다.
각 반복은 새 로컬 서버를 띄우고, 모델에 전달하지 않은 비공개 표식과 평가 오라클로 실제 정보 획득을 대조합니다.
결과는 `benchmarks/results/j25-*/result.json`에 저장됩니다. 이 합성 사례의 비율은 Juice Shop이나
일반 웹앱 전체 취약점 발견률을 뜻하지 않습니다. 인증된 브라우저 입력 검증과 복잡한 실제 로그인 흐름은
대상별 허가된 시험 신원과 범위가 필요합니다.
이번 장비의 3개 로컬 모델 비교와 Juice Shop 실행 결과는
`docs/superpowers/reports/2026-11-16-j25-evaluation.md`에 분모·분자와 제한을 함께 기록했습니다.

### 시스템 프롬프트 J2

서버를 재시작한 뒤 **시스템 프롬프트 → J2**를 선택합니다. J1과 기존 기본 선택은 유지합니다.
팀원 v4의 오프라인 입력 분석기를 가져오고, 현재 실행기에 기능별 후보 기록을 연결했습니다.
v4 브랜치 병합, 별도 평가 모델, 고정 트리 순회, HTTP 응답 자동 수집은 포함하지 않습니다.

- `discover_inputs(body, source_url, content_type='')`는 동기 함수입니다. 이미 읽은 HTML·JS에서
  같은 origin의 폼·입력·요청 선언·스크립트와 미해결 힌트를 요약합니다. 추가 요청을 보내지 않으며,
  선언된 경로나 문자열만으로 실제 엔드포인트·입력 처리·취약점이 확인되지는 않습니다.
  기본 요약은 종류별 20건, 스캔은 최대 200만 문자이며 제한에 걸리면 `truncated`를 표시합니다.
  외부 JS의 상대 요청은 페이지 기준 경로를 모르면 힌트로 남기며 모듈 import의 상대 경로와 구분합니다.
- 선택적 동기 함수 `note_candidate(name, basis='', next_observation='', state='open', evidence_paths=[])`로
  실제 기능·입력·인증 맥락별 후보를 기록합니다. 반환값의 `recorded/error`를 확인합니다.
  공격 유형이나 조사 순서, 매 단계의 결과 파일은 강제하지 않습니다. 한 실행 명령당 최대 16개,
  실행 전체에서 최대 64개 이름을 추적하며 원본 메모는 실행 로그에도 남습니다.
  기록 한도를 초과하면 누락 수를 보존하고 조사 미완료로 남깁니다.
- 메모는 출력 문자열과 분리된 워커 결과로 전달합니다. 상태는 `open/blocked/closed`이며 실패·시간 초과·중단
  단계의 메모로 후보를 완료 처리하지 않습니다. `closed`도 조사 중단 기록일 뿐 안전 판정이 아닙니다.
  `evidence_paths`는 최대 4개의 `work/`·`tools/` 상대 경로이며, 파일 내용의 진위는 독립 검증하지 않습니다.
- 다음 호출에는 최근 미완료 후보를 우선 제공합니다. 잘린 경우 원본 메모 `work/j2-memory.json`을 읽을 수 있고,
  전체 상태는 `session.json`의 `j2_state`에도 남습니다. 요약은 원본 경로와 최근 후속 작업을 유지합니다.
- J2는 문법·잘못된 도구 호출을 모델 응답 검증 단계에서 검사합니다. 거절한 코드는
  `tools/preflight-CALL-*.py`와 산출물에 보존하고 `not_run`으로 남깁니다. 수정 호출은 모델 예산을
  사용하지만 실제 실행되지 않은 명령은 도구 호출로 세지 않습니다.
- 이미 실패한 초기 무조건 import는 같은 환경에서 다시 실행하지 않습니다. try/except fallback이나
  준비 코드 뒤 import는 허용하고, 성공한 파일 쓰기·셸 명령 뒤에는 환경이 달라질 수 있어 캐시를 비웁니다.
  반복된 정상 응답·대조군·시간 초과를 일괄 차단하거나 고정 횟수 후 후보를 포기시키지는 않습니다.
- 후보 메모와 별도로 모든 실행의 상태·코드 경로·오류 종류·기존 요청 참조를 자동으로 기록합니다.
  기존 HTTP 도우미의 호출에서 URL·메서드·응답 상태만 최대 16건/명령 기록하며 URL의 자격증명·쿼리는
  제거합니다. 새 요청·자동 본문 저장은 하지 않고 원시 클라이언트나 모든 브라우저 요청을 수집하지 않습니다.
- 보고서에는 실행 기록 대조를 먼저 보여주고 모델의 미검증 보고를 뒤에 둡니다. `[step:N]`의 없는 단계와
  실패 단계를 표시하고 미시행 명령도 구분합니다. 단계 참조 대조는 문장 의미나 취약점의 독립 검증이 아닙니다.
- 미완료·차단 후보가 있거나 유효한 실행 관찰 없이 끝나면 `incomplete`(조사 미완료)로 보고합니다.
  후보 추적 없이 실행 실패가 남은 경우도 조사 미완료로 남깁니다.
  보고를 위한 `finish`는 허용합니다. 모든 기록을 닫았거나 실행 출력이 있어도 전체 사이트의 점검 완료나
  취약점 부재를 보장하지 않습니다. 마지막 모델 호출의 보고 예약은 50·60회 같은 사용자 설정에도 적용합니다.

J2의 파이프라인 진행 정보는 로컬 모델과 OpenRouter에 공통 적용됩니다.
공통 명령 검사는 `read_file`로 웹 URL을 여는 실수와 이미 실행 중인 루프를 `run_until_complete` 등으로
다시 구동하는 알려진 오류를 실행 전에 알려줍니다. J1/v4도 코드 검사를 모델 응답 수락 전에 적용하며,
J2는 기존 사전 검사·거절 산출물 경로를 유지합니다. 정상적인 별도 스레드 작업이나 사용자 정의 객체는
가능한 범위에서 구분합니다. 이 검사는 생성 코드의 정확성이나 모델의 보안 판단을 보장하지 않습니다.
셸에 직접 들어간 Python `await` 호출도 실행 전에 거절합니다. `browser_api` 호환 모듈은 기존 도구와
브라우저 객체를 그대로 제공하며 전역 모듈 상태나 대상 범위 제한은 바꾸지 않습니다. 잘못된 줄바꿈의
진단만 제공하고 생성 코드를 자동으로 다시 해석하거나 수정해 실행하지 않습니다.
내부 응답 수정 재시도에서도 최근 모델 호출 시간을 기준으로 보고 시간을 예약합니다. 실제 보고 생성
시간은 예측할 수 없으므로 이 예약은 시간 초과 방지의 보장이 아닙니다.
`work/j2-memory.json`은 현재 실행을 시작할 때 비어 있는 상태로 만들며 이전 실험 기록을 자동으로
불러오지 않습니다. `memory_state`에 현재 실행 전용 범위와 내부 메모리 읽기 횟수를 표시합니다.
빈 메모리는 조사 결과가 아니라 관찰 기록 부재입니다. 이 파일만 읽고 종료하면 `incomplete`로 남고,
내부 메모리 출력은 보안 영향 주장의 관찰 단계 참조로 인정하지 않습니다.
빈 시작 메모리와 새 작업 없이 반복하는 내부 메모리 읽기는 실행 전에 거절합니다. 메모리 읽기·거절 로그가
자동 저장되어 파일 내용이 바뀌어도 새 조사로 취급하지 않습니다. 다른 작업 후에는 다시 읽을 수 있으며,
일반 파일 읽기·대상 대조군·재검증에는 이 제한을 적용하지 않습니다. 수정에 실패해도 기존 모델 호출·보고 예산 안에서 종료합니다.
`j2.pending_resources`와 `finish_review`는 스크립트·내비게이션 단서의 선언, 기존 GET 응답 메타데이터,
명시적 `discover_inputs` 텍스트 분석을 구분합니다. 응답은 쿼리를 제거한 경로로만 대조하며,
분석 기록도 전체·최신 본문 확보나 의미 분석 완료를 보장하지 않습니다. 모든 단서 방문을 강제하지 않고
남은 단서·오류·제한을 종료 보고에 남깁니다. 상세 진행 목록은 최대 128개, 미확인 단서 미리보기는 6개이며 생략 수를 표시합니다.

선택적 후보 메모에는 `evidence_level='hypothesis'|'normal_behavior'|'controlled_comparison'|'security_effect'`와
`observation_steps=[1, 2]`를 지정할 수 있습니다. 단계 참조는 최대 8개이고, 이전 단계의 정상 실행 출력 존재만
대조합니다. 해당 출력의 의미·재현성·보안 영향은 독립 검증하지 않으며 **모든 수준이 모델 주장**입니다.
기존 호출은 그대로 동작하고, 수준·참조를 생략하면 이전 값을 유지합니다. 명시적 초기화는
`evidence_level='hypothesis', observation_steps=[]`를 사용합니다.

J2의 일반 행동 설명은 `plan` 최대 240자, `reason` 최대 800자로 요청하고 응답도 검사합니다.
코드·파일 본문·최종 보고서의 길이는 이 제한으로 줄이지 않습니다. 출력이 아직 끝나지 않은 설명의
반복으로 잘리면 같은 출력 예산으로 복구를 요청하며, 정상적인 코드 생성이나 추론 길이 부족에 대한
기존 출력 예산 확대는 유지합니다. 이 보정은 실제 모델의 지침 준수나 발견 성과를 보장하지 않습니다.

오류 이력은 의존성·코드·런타임·시간 초과·하네스 제한·접근 응답을 구분합니다. 내비게이션 실패와 이후
같은 공개 경로의 도우미 완료를 연결하지만, 서로 다른 쿼리·입력일 수 있어 원인 해결로 단정하지 않습니다.
일반 출력만 있는 성공 명령은 복구로 처리하지 않습니다. 점수 화면의 ‘실행 출력’은 발견 수가 아니며,
진행 기록과 미검증 보안 영향 주장을 별도로 표시합니다. 독립 검증 기능이 없는 `verified_findings`는 `null`입니다.

긴 실행 출력과 파일 읽기는 65,536자 안에서 앞·뒤를 보존하고 중간 생략을 표시합니다.
J2는 이미 제공된 도구를 `from tools import http_get`처럼 가져올 수 있으며, 브라우저 객체는
`from browser import page`로 가져올 수 있습니다. 개별 도우미 이름은 모듈이 아닙니다.
미설치 모듈 목록과 도구의 정확한 반환 형태는 다음 호출에도 전달합니다.
마지막 `finish`가 보고서 본문을 `content`에 넣은 경우, 실행 입력이 없을 때만 기존 설명과 함께
`reason`으로 보존합니다. 추가 모델 호출이나 파일 쓰기로 바꾸지 않으며 원래 응답은 로그에 남습니다.
보고 호출의 출력 스키마도 `finish`로 한정합니다.
파일의 원본과 실행 출력 로그는 유지합니다. 최근 결과의 `path`와 이력의 `source_path`는
런타임 안의 상대 경로이므로 작업 코드를 다시 읽을 수 있습니다. 동기 도우미에 잘못 붙인
`await`는 실행 전에 검사하며, 사용자가 정의한 같은 이름의 함수에는 이 검사를 강제하지 않습니다.

### 시스템 프롬프트 J1


서버를 재시작하고 새 실험 화면의 **시스템 프롬프트 → J1**을 선택합니다.
파일은 `prompts/system/J1.txt`이며 이전 프롬프트 원문은 유지됩니다. 현재 기본 선택은 `planning.py`를 따릅니다.
목표 입력 방식은 같습니다. J1을 선택한 실행에만 다음 제어가 적용됩니다.

- 관찰된 기능·입력·객체·표시 맥락과 권한을 근거로 조사할 후보를 선택합니다. 유형별 고정 순서나
  필수 점검 목록은 없습니다. 보고서에는 관찰 근거가 있는 유망 후보나 실제 시도한 항목만 포함합니다.
  제한된 시험에서 문제가 확인되지 않았다는 결과를 취약점 부재나 안전성 입증으로 표현하지 않습니다.
  `CHECK/STAGE:` 표기와 `reason`의 `[step:N]` 참조는 후보 추적을 돕는 선택 사항입니다. 빠지거나 맞지 않아도
  명령은 실행되며, 해당 단계는 후보 진행에 반영하지 않고 `unlinked_steps`와 `advisories`에 남깁니다.
  코드가 검사하는 것은 참조 존재와 단계 순서이며 HTTP 진위나 후보의 실제 적합성까지 검증하지는 않습니다.
  관찰된 후보의 전제가 없으면 `blocked`, 아직 평가하지 않은 항목은 미평가로 남깁니다. 조기 종료도 가능합니다.
- 기준 단계 번호별로 후보를 분리해 같은 유형의 다른 입력을 조사해도 이전 후보의 진행 상태를 보존합니다.
  `candidate_refs`에서 최근 후보를 참고하고, 해당 후보의 기준·비교 단계 번호로 다시 이어갈 수 있습니다.
- 기준 단계에서 실행된 코드의 경로·해시·읽을 수 있는 요청 필드를 별도로 보존합니다(최근 최대 8개).
  같은 요청 형식이라도 새 기준 코드를 기억해 오래된 토큰·인증 정보를 재사용하지 않도록 합니다.
  비교·검증 중 요청 URL·메서드·필드가 달라지면 안내를 남기되 실행을 막지 않습니다. 의도한 변경도
  보안 판단에 사용할 수 있도록 이유와 실제 응답 차이를 확인해야 합니다.
  동적으로 만든 요청은 필드를 읽지 못할 수 있으며, 코드 실행 성공은 HTTP 성공의 독립 증거가 아닙니다.
  `form_fields: null`은 추출 불가를 의미합니다. 필드가 없는 요청으로 판단해 차단하지 않습니다.

세션의 `j1_state.coverage`는 유형별 최근 요약이며, 전체 후보의 단계·미검증 사유는 `j1_state.candidates`,
최근 기준 코드 참조는 `j1_state.request_memory`에 남습니다. 모델 보고 실패 시에도 후보별 상태를 보고합니다.
자동 보고서에서 `not_started` 유형은 제외합니다.
`reviewed_unverified`는 단계가 실행됐다는 뜻이며 취약점 확정이나 방어 입증이 아닙니다.
HTTP 증거 수집기는 추가하지 않았습니다. 실제 탐지율·호출 효율 개선은 같은 조건의 비교 실험이 필요합니다.
변경 상세는 `prompts/system/CHANGELOG.md`에 기록합니다.

### 주요 파일

- `app.py`: FastAPI API와 실행 관리
- `explorer.py`: 브라우저 관찰, LLM 계획 실행, 가설 실험 및 응답 비교
- `model_providers.py`: OpenRouter 모델 목록, 설정 변환 및 스트리밍 어댑터
- `planning.py`: 계획 스키마, 모델 지시문, 결정 검증
- `j1_policy.py`: J1 관찰 참조·후보 단계 검사, 기준 코드 참조 보존, 컨텍스트 미리보기 압축
- `browser_http.py`: 대상 origin 검사, 기존 HTTP 도우미, 브라우저 폼 요청 재사용
- `lab.py`: 로컬 Juice Shop 컨테이너 상태 확인과 시작
- `static/`: 대시보드
- `tests/`: 테스트
- `Version/`: v1·v2 설계 문서

## 개발 상태

MVP 실험 단계입니다. 검색 입력은 연결된 레이블, 접근성 이름과 상위 검색 영역을 함께 읽어 인식하며, 숨겨지거나 접힌 입력은 선택지에서 제외합니다.
계획, 탐색 순서와 검색값은 LLM이 선택합니다. 실행기는 화면 상태별 실패·변화 없는 행동과 반복 전환을 제한하고 그 이유를 모델에 전달합니다. 같은 입력에서 다른 검색값은 선택할 수 있습니다.
실행할 수 없는 선택이 3회 연속 이어지면 `탐색 정체`로 종료하며, 모델 연결·응답 생성 오류는 별도로 표시합니다. 실행 데이터, 로그, 로컬 의존성은 Git 저장소에서 제외됩니다.
