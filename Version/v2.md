# MVP v2 — 블랙박스 웹 정찰·가설 실행 에이전트

## 2026-10-12 수정 — LLM이 탐색 계획과 행동을 결정

- 시작 URL을 연 뒤에는 **관찰 → LLM 계획·다음 행동 선택 → 검증·실행 → 결과 전달 → 재계획**을 반복한다. 검색어, 탐색 순서, 예시 변경값을 코드에 고정하지 않는다.
- LLM은 현재 화면의 관찰된 요소 ID를 사용해 `click`, `search`를 선택하거나, 실제 관찰된 조회 요청 ID로 `experiment`를 선택한다. 계획이 충족됐거나 더 진행할 근거가 없으면 `finish`를 선택한다. 새로운 경로나 셸 명령을 만들지는 않는다.
- 프로그램은 대상·조회 동작·근거 ID·현재 요소·예산을 검사하고 선택된 행동을 실행한다. 잘못된 선택과 실행 실패는 사유를 모델에 돌려준다. 모델 오류 시 규칙 기반 탐색으로 대체하지 않는다.
- 검색 동작뿐 아니라 초기 페이지와 다른 UI 동작에서 관찰된 GET·JSON 조회 요청도 가설 후보로 제공한다. 정적 JS 경로는 실제 요청으로 확인하기 전까지 후보로 보존한다.
- 모델 입력에는 화면 문구, 허용 동작이 붙은 요소 목록, 요청·응답 구조와 작은 데이터 표본, 현재 계획, 최근 선택, 가설과 실험 결과가 포함된다. 사이트 제공 내용은 명령이 아닌 관찰 데이터로 취급한다.
- 기본 한도는 화면 행동 10회, 가설 3개, 의사결정 20회, 실행 10분이다. LLM이 계획한 횟수를 강제로 채우지 않는다. 동일 화면의 동일 행동과 동일 요청·변경값 조합은 반복하지 않는다.
- 대시보드는 현재 계획과 최근 결정·선택 이유·실행 상태를 표시한다. 내보내기에 `planner_version`, `plan`, `decisions`, `finish_reason`을 추가하고 행동 및 가설에 `decision_id`를 연결한다.
- 자유 텍스트 예측은 자동 참/거짓 판정하지 않는다. 비교 결과는 `변화 관찰`, `변화 미관찰`, `판단 보류`, `실행 실패`로 기록하고 `hypothesis_verdict: 미판정`을 표시한다. 응답에 변경 문자열이 있다는 이유로 예측이 맞았다고 표시하던 판정을 제거했다.
- Ollama는 선택한 설치 모델을 사용하며 `think:false`를 유지한다. 계획·선택 이유·가설 JSON은 실시간 콘솔에 출력한다.

아래 원안의 단방향 실행 흐름과 결과 분류는 위 수정 사항으로 대체한다.

## 목표와 완료 범위

에이전트는 **대상 URL 하나만** 입력받아 웹사이트를 관찰한다. 브라우저에 공개된 HTML·JavaScript·CSS, 렌더링된 DOM, 실제 HTTP 요청과 응답에서 근거를 수집한다. 로컬 Ollama 모델이 그 근거로 검증 가능한 가설을 만들면, 프로그램이 한 조건만 바꾼 실험을 실행하고 기준 요청과 결과를 함께 기록한다.

v2의 완료 지점은 `관찰 → 가설 → 기준 실행 → 단일 변경 실험 → 응답 비교`이다. 응답이 달라졌다는 사실만으로 취약점이라고 판정하지 않는다. 자동 취약점 확정, 다단계 공격 연쇄, 계정·결제·데이터 변경 동작은 후속 버전의 과제다.

첫 실습 대상은 사용자가 실행 중인 `http://127.0.0.1:3000/`의 OWASP Juice Shop이다. 실험 시작 전에 에이전트에 경로 목록, 취약점 정답, 서버 소스, 계정 정보를 주지 않는다. 백엔드는 기존 FastAPI, 모델은 로컬 Ollama `qwen3.5:2b`, 대시보드는 기존 로컬 웹 화면을 확장한다. OpenRouter/Jev 연동은 이번 범위에 넣지 않는다.

## 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| FastAPI 실행 관리자 | 실행 ID, 상태, 중지·초기화, 예산, 이벤트 전달을 관리한다. |
| 브라우저 정찰기 | JavaScript를 실행한 화면의 DOM과 행동별 네트워크 요청·응답을 수집한다. Python Playwright를 사용한다. |
| 근거 저장소 | 화면, 요소, 사용자 행동, 요청, 응답을 ID로 연결한다. |
| Ollama 가설 생성기 | 관찰 근거 중 작은 묶음을 받아 한 번에 가설 하나를 구조화된 JSON으로 제안한다. |
| 실험 실행기 | 가설의 근거와 실행 조건을 검사하고 기준 실행과 단일 변경 실험을 수행한다. |
| 비교기·대시보드 | 두 실행의 차이와 오류를 보여주고 JSON으로 내보낸다. |

Playwright는 페이지의 요청·응답과 `fetch`/XHR을 관찰하고 버튼 동작 뒤의 응답도 연결할 수 있다. 따라서 모델에 화면 이미지를 보낼 필요 없이 DOM과 네트워크 기록을 구조화해 전달한다. 참고: [Playwright 네트워크 문서](https://playwright.dev/python/docs/network).

## 1. URL에서 정찰 시작

1. 시작할 때 새 브라우저 컨텍스트를 만들고 대상 URL을 연다. 실행마다 쿠키와 페이지 상태를 분리한다.
2. 초기 HTML과 로드된 JavaScript·CSS 파일의 URL을 기록한다. JavaScript에서는 경로·API·매개변수로 보이는 문자열을 **후보**로만 추출한다. CSS는 요소의 표시 상태를 이해할 때만 보조 자료로 쓴다.
3. JavaScript 실행이 끝난 DOM에서 현재 URL, 제목, 링크, 폼, 입력란의 이름·유형·레이블, 버튼의 텍스트·상태를 수집한다. 비밀번호 입력값과 쿠키 값은 모델 요약 및 화면에 싣지 않는다.
4. 링크 이동과 검색·필터·페이지 이동처럼 조회 성격의 UI 동작을 제한된 횟수만 수행한다. 각 동작에 `행동 ID → 전후 DOM → 발생한 요청 ID → 응답 ID` 관계를 남긴다.
5. 요청에는 메서드, URL, 경로, 쿼리·본문의 키와 값 유형, 상태 코드, 리다이렉트, 콘텐츠 유형, 응답의 짧은 요약을 기록한다. 필요한 원문은 크기를 제한해 별도로 보존한다.
6. SPA 경로와 서버 API를 구분한다. 임의 경로가 시작 HTML과 같은 HTTP 200을 돌려줘도 유효한 API나 화면으로 확정하지 않는다. 실제 UI 동작에서 발생한 요청을 정적 JS 문자열보다 강한 근거로 취급한다.

화면의 텍스트와 사이트가 제공한 코드·응답은 관찰 데이터다. 그 안의 명령문을 에이전트 지시로 취급하지 않는다.

## 2. 근거를 가설로 변환

정찰기가 긴 HTML·압축 JavaScript 전체를 모델에 넣지 않는다. 화면별 요소 목록, 관찰된 요청 예시, 응답 요약, 관련 코드의 짧은 발췌를 근거 ID와 함께 전달한다. `qwen3.5:2b`가 처리할 수 있도록 한 번에 화면 하나와 요청 몇 개로 범위를 줄인다.

가설 JSON에는 다음 필드를 요구한다.

| 필드 | 의미 |
| --- | --- |
| `evidence_ids` | 실제 관찰 기록의 ID. 없는 ID를 참조하면 폐기한다. |
| `claim` | 무엇을 확인하려는지 한 문장으로 쓴다. |
| `baseline` | 관찰된 정상 UI 동작 또는 요청을 어떻게 재실행할지 지정한다. |
| `change` | 입력값·쿼리값 등 바꿀 **한 가지** 조건을 지정한다. |
| `expected_observation` | 가설이 맞다면 어떤 응답 또는 화면 차이가 나올지 쓴다. |
| `required_state` | 필요한 페이지·세션 상태를 지정한다. 충족할 수 없으면 실행하지 않는다. |

예를 들어 검색창과 검색 요청을 실제로 관찰했다면, 정상 검색어와 특수문자가 들어간 검색어의 처리 방식에 차이가 있는지 가설을 만들 수 있다. 실험값은 짧고 무해한 값으로 시작한다. 발견하지 않은 경로·매개변수를 모델이 임의로 만들어 내면 실행하지 않는다.

Ollama에는 JSON 스키마 형식 출력을 요청한다. 형식 오류 시 한 번만 재시도하고, 다시 실패하면 `가설 생성 실패`를 기록한다. 규칙 기반 대체 선택으로 가설이 만들어진 것처럼 표시하지 않는다. 참고: [Ollama 구조화 출력 문서](https://docs.ollama.com/capabilities/structured-outputs).

## 3. 기준 실행과 단일 변경 실험

1. 실행기는 가설의 근거 ID, 실제 관찰된 대상, 현재 세션, 대상 URL 범위, 요청 예산을 먼저 확인한다.
2. 원래의 UI 동작이나 요청을 같은 브라우저 세션에서 다시 실행해 **기준 결과**를 얻는다. 원래 결과와 기준 결과가 크게 흔들리면 실험은 `판단 보류`로 남긴다.
3. 가설이 지정한 한 조건만 바꾸어 다시 실행한다. 나머지 경로, 메서드, 세션, 입력은 동일하게 유지한다.
4. 두 실행의 요청·응답 원문과 정규화된 비교값을 함께 보관한다. 상태 코드, 리다이렉트, JSON 구조·값, 오류 메시지, 결과 목록, 화면 문구를 비교한다. 시간·길이 차이는 참고 정보로만 표시한다.
5. 결과를 `예상한 변화 관찰`, `변화 미관찰`, `판단 보류`, `실행 실패` 중 하나로 기록한다. 각 판정에서 어떤 실제 필드가 달랐는지 보여준다.

초기 자동 실행은 탐색 중 발견한 조회 동작에 한정한다. 로그인, 장바구니, 주문, 설정 변경과 같이 서버 상태를 바꾸는 UI는 관찰 목록에 남기되 자동 실험 대상으로 선택하지 않는다. 모델은 실행 가능한 명령 문자열을 직접 만들지 않고, 구조화된 행동·근거·변경값을 제안한다. 브라우저 조작과 HTTP 호출은 프로그램이 수행하며 대시보드에는 재현용 요청 정보를 표시한다.

## 실행 한도와 중지

- 시작 URL과 같은 출처의 로컬 Juice Shop으로만 이동·실험한다. 외부 리다이렉트와 페이지가 유도한 다른 호스트 요청은 실행기에서 차단한다.
- 첫 기본값은 화면 이동 10회, 가설 최대 3개, 가설당 실험 1개, 전체 실행 시간 10분이다. 브라우저가 자동으로 가져오는 리소스 요청 수와 에이전트 행동 수를 별도 계수로 표시한다.
- 중지를 누르면 새 행동을 시작하지 않고 진행 중인 작업을 취소한 뒤 브라우저 컨텍스트를 닫는다. 종료 후 늦게 도착한 이벤트가 화면 상태를 다시 바꾸지 않도록 실행 ID를 확인한다.
- 결과가 3개 미만이어도 근거가 없으면 가설을 채우기 위해 임의 생성하지 않는다. 모델 실패, 시간 초과, 건너뛴 동작은 각 사유를 기록한다.

## 대시보드 변경

기존 시작·중지·JSON 다운로드 옆에 **초기화** 버튼을 추가한다. 초기화는 실행을 중지하고 브라우저 세션과 현재 화면의 단계·가설·로그를 0으로 되돌린다. 이미 다운로드한 JSON과 Juice Shop 데이터는 건드리지 않는다. 새로고침이나 서버 시작만으로 탐색이 자동 실행되지 않게 한다.

화면에는 현재 단계(`정찰/가설 생성/기준 실행/실험/비교`), 발견한 화면·입력·요청 수, 가설별 근거, 실행 중인 행동, 기준 응답과 실험 응답의 차이를 순서대로 보여준다. 모델의 내부 추론 대신 사용자에게 설명할 수 있는 짧은 가설·선택 이유만 표시한다. `진행 단계`는 에이전트가 수행한 행동 수로 정의하고, 브라우저의 자동 리소스 요청 수는 별도 표시한다.

## JSON 기록 형식

내보내기에는 `run_id`, 대상 URL, 모델, 시작·종료 시각, 한도, 중지·초기화 상태를 포함한다. `observations`에는 화면·요소·행동·요청·응답을 ID로 저장하고, `hypotheses`에는 근거 ID와 실행 가능 여부를 저장한다. `experiments`에는 가설 ID, 기준 실행 ID, 변경 실행 ID, 차이, 결과 분류, 오류를 저장한다. 화면에 보이는 요약에서 원래 관찰까지 따라갈 수 있어야 한다.

## 구현 순서와 검증

1. **브라우저 정찰**: FastAPI 실행 관리자에 Playwright 컨텍스트를 연결한다. Juice Shop 시작 URL만으로 렌더링된 검색창 등 실제 DOM 요소와 그 행동에서 발생한 API 요청을 연결해 기록한다.
2. **근거 구조화**: 화면·행동·요청·응답 ID, 중복 제거, SPA 응답 구분, 모델용 요약을 만든다. 공개된 JS 문자열만 있는 경로는 후보로 남긴다.
3. **가설 생성**: Ollama 스키마, 근거 ID 검사, 한 조건 변경 검사, 실패 기록을 넣는다. 모델이 존재하지 않는 ID나 입력을 제안하면 실행하지 않는지 확인한다.
4. **실험과 비교**: 실제 관찰 요청의 기준 실행과 변경 실행을 수행한다. 같은 조건이 유지됐는지, 차이의 근거가 저장됐는지 확인한다.
5. **대시보드**: 단계·근거·가설·비교 화면과 초기화 버튼을 붙인다. 중지 후 늦은 이벤트, 초기화 후 0 표시, JSON 내보내기를 확인한다.
6. **통합 실습**: 에이전트에는 Juice Shop URL만 주고 한 번 실행한다. 별도의 사람이 기록을 살펴 근거가 실제 화면·요청에서 나왔는지 확인한다.

v2 합격 기준은 URL 하나로 동적 화면과 실제 요청을 관찰하고, **관찰 ID에 연결된 가설 최소 1개**를 기준 실행과 단일 변경 실험까지 재현해 JSON과 대시보드에서 추적할 수 있는 것이다. 3개 가설·2개 실험은 실습 관찰 목표이며, 근거가 부족하면 억지로 수를 맞추지 않는다. 출처 밖 실행 0건, 중지·초기화 정상 동작, 응답 차이를 취약점으로 자동 확정하지 않는 것도 확인한다.

## 실행 및 구현 상태

`python app.py` 또는 `run.cmd`로 대시보드를 열고 `http://127.0.0.1:8765/`에서 시작한다. 새 환경에서는 `python -m pip install -r requirements.txt`와 `python -m playwright install chromium`을 먼저 실행한다. 브라우저 요청과 실험은 로컬 Juice Shop의 조회 요청으로 제한된다.

2026-09-28 통합 실습에서는 시작 URL만 입력해 검색 UI를 관찰하고, 검색 요청과 응답 ID를 인용한 가설 1개를 생성했다. 동일 세션의 기준 요청과 쿼리 값 하나를 바꾼 요청을 실행해 상태·JSON 목록 길이·값 차이를 기록했다. 중지와 초기화 후 실행 단계·관찰·가설·로그가 0으로 돌아오는 것도 확인했다. 이 결과는 취약점 판정이 아니다.
