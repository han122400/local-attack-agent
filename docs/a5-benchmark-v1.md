# A5 고정 실습 비교 · a5-paired-v1

## 목적과 사전 고정

한 쌍의 v3/v4 실행으로 탐색·판정 경로가 실제 고정 실습 환경에서 작동하는지 확인한다. 한 쌍은 성능 우위의 통계적 증거가 아니다. 첫 조건은 [`benchmarks/a5-pair-v1.json`](../benchmarks/a5-pair-v1.json)의 비유도 탐색이고, 두 번째 조건은 [`benchmarks/a5-guided-v1.json`](../benchmarks/a5-guided-v1.json)의 알려진 검색 입력 지점이다. 각 쌍 내부에서는 목표가 같다. 실행 시 파일의 SHA-256, 실행 모델의 Ollama digest, 두 프롬프트 SHA-256, Decisions 카탈로그의 버전 명시 모델 ID·canonical slug를 기록한다. 목표 문구·모델·온도·시드·컨텍스트·출력 한도·대상·시간/모델 호출/명령 예산은 같은 쌍의 두 방식에 같다. v4만 별도 scorer와 노드/오라클 한도를 사용한다. 실행 LLM은 두 방식 모두 로컬이라 API 비용 0이며, 유료 호출은 v4의 scorer뿐이다. 이 비교는 동일한 시간·호출 상한과 실제 API 비용을 기록하지만, scorer가 없는 v3와 v4의 금전 지출 상한이 동일하게 작동했다는 뜻은 아니다.

순서는 v3 → v4다. 매번 고정된 `juice-lab` 이미지·루프백 포트·마운트 없음 조건을 확인하고 컨테이너를 재시작한다. 재시작 후 `dbSchemaChallenge`가 미해결인지 확인한다. 실행 중 수집기가 아닌 대상 요청은 에이전트가 생성한다. 정리 단계의 재시작 **직전** 동일 챌린지의 해결 여부와 컨테이너 식별자를 별도로 캡처한다. 실행의 초기화·정리·외부 scorer 카탈로그 확인은 탐색 시간 예산과 분리하되 전체 wall 시간에도 기록한다. 단독 실습 환경 선언은 명시적인 `--exclusive-lab`이 있어야 한다.

v3의 브라우저는 에이전트가 대상 상태를 읽는 실행 도구다. 이 단계에서 대시보드의 화면 품질 검사, 스크린샷, Playwright UI 테스트는 실행하지 않는다. v4의 판정 모델 입력은 A3의 범주형 투영을 따른다. 기존 `.env`의 OpenRouter 키는 상위 프로세스의 판정 어댑터에만 읽고, 실행 모델과 그 명령의 환경변수에 넣지 않는다.

## 측정·판정 규칙

| 항목 | 비교 방법 |
| --- | --- |
| 알려진 정답 1건 | 종료 직전 `dbSchemaChallenge.solved`를 두 방식 모두 같은 1차 관측값으로 본다. 초기 미해결 및 컨테이너 동일성이 깨지면 비교 결과는 무효다. |
| 자동 확정 | v4 `report.json.stats.confirmed`만 하네스 확정으로 센다. v3의 `evidence=true`는 관찰 존재만 뜻하므로 확정 건수로 바꾸지 않는다. |
| 오탐 | 확정 주장과 독립 관측이 모순되는 경우에만 센다. v4의 확정 건수와 종료 직전 정답 상태가 어긋나는지 자동 표시한다. v3의 자유 서술 주장은 이벤트 근거를 수동 판정한다. 단순 미확정은 오탐이 아니다. |
| 중복 | v3의 동일 관찰 digest 반복, v4의 dedup된 발견 이벤트를 각각 기록한다. 두 값의 단위가 다르므로 직접 우열 비교하지 않는다. 동일 경로·입력·가설의 실제 재시도는 보존 로그를 수동 확인한다. |
| 사용량 | 실행 LLM의 모든 요청·재시도, v4 scorer의 실제 요청, 명령 실행, 토큰·지연·API 비용을 분리한다. 로컬 LLM API 비용은 0이고 scorer 비용은 별도 및 총합으로 기록한다. 미확정 비용은 0으로 대체하지 않는다. |

실행 모델 프롬프트가 다르고 v4에는 scorer 호출이 모델 호출 총량에 포함된다. 따라서 같은 총 한도는 각 방식에 같은 *자원 상한*을 주지만, 실행 LLM 요청 수가 같다는 뜻은 아니다. 순서·캐시·한 쌍의 표본 때문에 품질 차이의 인과 결론을 내리지 않는다. 고정 챌린지 외 취약점 종류의 미확정 결과는 안전 판정으로 해석하지 않는다.

## 실행

```powershell
python a5_benchmark.py
python a5_benchmark.py --execute --exclusive-lab --env-file 'C:\Users\vinny\Desktop\personal_project\Local attack agent\.env'
python a5_benchmark.py --config benchmarks/a5-guided-v1.json --execute --exclusive-lab --env-file 'C:\Users\vinny\Desktop\personal_project\Local attack agent\.env'
```

첫 명령은 네트워크·브라우저·컨테이너에 손대지 않는 설정 확인이다. 두 번째 명령은 실제 실습을 실행하고 `runs/a5_pairs/<pair_id>.json`과 각 `runs/<run_id>/`에 근거를 남긴다. 실습 컨테이너를 다른 작업이 사용 중이면 `--exclusive-lab`을 주지 않는다. 중단/정리 실패 시 쌍을 완료로 표시하지 않고 기존 run의 복구 절차를 먼저 따른다. API·대시보드의 v3/v4 방식 선택 UI는 B 단계다.

## 첫 조건 관측

비유도 첫 쌍은 `runs/a5_pairs/eed763e793c542b5b271fdf457ed5856.json`에 저장했다. v3는 10번의 실행 모델 호출과 9번의 명령 실행 중 7번의 실패를 기록했으며, SQLi/XSS/IDOR를 실제 검사하기 전에 종료했다. v4는 실행 모델 2번·명령 2번에서 결과 파일 2개를 만들었으나 두 파일 모두 계약 위반으로 가져오지 못했고, 자식 노드·scorer 호출은 0이었다. 두 방식 모두 종료 직전 고정 챌린지가 미해결이었다. 이 결과는 위험도 탐색의 성능을 측정한 것으로 취급하지 않는다.

v4 실패 중 하나는 절대경로의 결과 JSON을 자기 증거로 참조한 것이고, 다른 하나는 `next_observation`을 빠뜨리고 앞선 결과 JSON을 증거로 참조한 것이다. v4 모델 입력에 ID가 채워진 결과 템플릿을 제공하고 결과 JSON을 증거로 쓰지 못하게 계약을 강화했다. 첫 쌍의 원본 파일은 변경하지 않았다.

첫 비교 기록기에서도 외부 사전 초기화 후 v3 컨트롤러가 한 번 더 초기화했는데, 비교 기준으로 사전 초기화 시각을 사용해 동일 컨테이너 판정이 거짓이 되는 오류가 있었다. 실행 중 저장한 후속 컨테이너 식별자와 `initial_lab_reset` 이벤트의 순서를 확인해 `effective_baseline_identity`를 별도 기록하고 집계를 다시 계산했다. 원본 run 로그는 변경하지 않았다. 다음 실행부터 기록기가 컨트롤러 초기화 직후의 식별자를 자동 기준으로 사용한다.

## 알려진 입력 지점 조건과 수동 판독

유도형 첫 쌍은 `runs/a5_pairs/eb9a048adb5c4c4db00ee590cec2ae9f.json`에 저장했다. 두 방식 모두 동일한 `qwen3.5:9b` digest, 600초 탐색 상한, 모델 호출 24회·명령 24회 한도, 동일한 검색 입력 힌트와 초기 미해결 실습 상태를 사용했다. v3는 실행 모델 11회·명령 10회(실패 5회), v4는 실행 모델 10회·Jev 2회·명령 6회(실행 실패 0회)를 기록했다. v4 판정 비용은 `$0.000073878`, 로컬 실행 모델 API 비용은 0이었다. 두 방식 모두 종료 직전 챌린지 미해결, 같은 컨테이너였고 하네스가 확인한 취약점은 0건이었다. v4는 표면 2개를 저장했지만 후보는 0개였다.

v3의 `evidence=true` 관찰 5개는 독립 확인 건수가 아니다. 보존된 10번째 관찰은 HTTP 500을 근거로 SQLi를 확인했다고 썼으나 SQL 의미의 재현 근거가 없어 **근거 부족 확정 주장 1건**으로 수동 판독했다. 이 실습 경로에는 실제 SQLi가 있으므로 취약점 존재 자체의 오탐으로 세지 않았다. v4의 한 결과도 표면에 `proposed_verdict=confirmed`를 썼지만 후보·오라클 증거가 없어 보고서는 확정 0건을 유지했다. 각 쌍의 `manual_review`에 판독 근거를 기록했다. 두 방식의 자동 확정 수가 같다는 사실은 탐색 품질이 같다는 뜻이 아니다.

이 실행에서 v4 모델은 시험값이 달라진 `q` URL을 새 `surface`로 등록했다. 결과 가져오기 경계에서 새 발견의 URL을 입력 이름만 남기는 형태로 정규화하고, 프롬프트에 시험값과 취약점 가설을 구분하도록 명시했다. 원본 결과 파일은 보존하며 이미 저장된 이벤트의 재생 규칙은 바꾸지 않았다. 두 과거 v4 run의 이벤트를 새 코드로 읽어 기존 노드 수가 그대로인 것도 확인했다. 수정 전 쌍의 지표를 수정 후 성능으로 해석하지 않는다.

## 수정 후 같은 조건 재실행

수정 후 유도형 쌍은 `runs/a5_pairs/bce41fbdb5534809b22d3438d41115b6.json`에 저장했다. 설정 SHA-256은 첫 유도형 쌍과 같고, v4 프롬프트 SHA-256은 새 값으로 남겼다. 매 방식 직전 초기화와 종료 직전 챌린지·동일 컨테이너 검사가 모두 통과했다.

| 방식 | 실행 LLM / Jev 호출 | 명령 / 실패 | 탐색 시간 | API 비용 | 챌린지 해결 | 하네스 확정 |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| v3 | 11 / 0 | 10 / 5 | 518.177초 | $0 | 아니오 | 판정 기능 없음 |
| v4 | 6 / 1 | 6 / 2 | 252.015초 | $0.000036708 | 아니오 | 0건 |

v4는 루트에서 검색 입력 표면 1개를 발견하고 Jev 평가 1건을 기록했다. 표면 조사에서 생성 코드가 2회 실패해 결과는 실패한 시도의 관찰로 가져왔고, SQLi 후보·오라클 호출은 0건이었다. 이 run에는 시험값 URL의 중복 발견 제출 자체가 없으므로 라이브 결과만으로 정규화의 효과를 입증하지 않는다. 별도 가져오기 회귀 테스트에서 같은 입력의 시험값 URL이 새 노드를 만들지 않음을 확인했다. v3 역시 응답 차이와 오류를 관찰했지만 확정 근거를 얻지 못했다. 저장된 이번 v3 보고서에는 명시적 취약점 확정 주장이 없었다.

세 쌍은 비교 실행 경로와 기록·비용 집계가 작동한다는 근거다. 로컬 9B 모델에서 확인된 SQLi 후보가 0개여서 탐욕 탐색의 취약점 발견 우위나 확인 정확도를 비교할 표본은 생기지 않았다. v4의 호출·시간이 적은 것은 트리 조기 소진과 코드 실패도 포함한 결과이므로 효율 향상으로 단정하지 않는다. 두 방식 모두 이 고정 사례를 해결하지 못했다는 한계까지 A5 결과로 보존한다.

## 별도 실습 양성 확인

모델 탐색 성과와 분리한 고정 양성 확인은 `runs/a5_smokes/31fd8636e4eb448d80fff5a1871f3598/summary.json`에 보존했다. 실습을 초기화하고 알려진 검색 SQLi 입력을 한 번 실행한 뒤, 하네스가 직접 챌린지 `false→true`, 같은 컨테이너, 일반 검색 대조군 음성, 임의 SQL 표식 2회 양성을 확인했다. 오라클 정책의 결과는 `confirmed`였고 HTTP 근거 5개를 보존했다. 이 입력은 고정 시험 fixture가 제공한 것이므로 v3/v4 모델이 취약점을 발견했다는 성과로 세지 않는다. 종료 후 다시 초기화해 챌린지가 미해결임을 확인했다.

첫 실호출에서는 대상의 압축 응답을 `httpx2`가 해제하지 못해 수집이 중단됐다. 오라클 요청에 `Accept-Encoding: identity`를 명시한 후 동일한 양성 확인이 통과했다. 실패한 시도의 run과 요약도 `runs/a5_smokes/`에 남겼다.
