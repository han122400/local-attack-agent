# J2.5 설계: 코드가 실행하고 로컬 모델이 판단하는 조사

## 목적

J2.5는 제한된 성능의 로컬 LLM으로도 관찰에서 후보 시험까지 이어지도록, 모델에게 Python·셸 코드와 결과 파일 작성 대신 다음 조사 선택과 그 이유만 요청한다. 실제 웹 접근, 입력 추출, 정해진 비교, 증거 연결, 예산·오류·종료 처리는 코드가 수행한다. 취약점 발견 성능의 향상 여부는 별도로 측정하며 이 설계만으로 주장하지 않는다.

사용자는 코드가 실행하고 모델이 매 단계 판단하는 방식을 선택했다. 각 모델 호출 전에 코드가 현재 단계에 필요한 정해진 관찰을 모을 수 있으며, 모델은 보존된 관찰의 범위 안에서 다음 행동을 고른다.

## 검토한 방식

1. 코드가 정해진 정찰과 시험을 일괄 수행하고 모델은 마지막에 검토한다. 모델 부담은 가장 적지만 화면과 입력에 따라 조사 방향을 바꾸기 어렵다.
2. **선택한 방식:** 코드가 실행 가능한 행동과 관찰을 제공하고 모델이 다음 후보·행동·시험값을 선택한다. 모델 호출이 필요하지만 관찰에 따라 조사 방향을 바꿀 수 있다.
3. v4.5의 트리·별도 scorer·모델 작성 실행 코드를 통째로 이식한다. 시도와 출처 관리는 참고할 만하지만, 작은 모델의 코드 작성 부담이 남고 J2와 실행 구조가 크게 다르다.

## 기존 기능과 적용 범위

- 새 시스템 프롬프트 ID는 `J2.5`다. 대시보드의 기존 프롬프트 선택과 실행 API에서 선택하며 기본값과 J1/J2/v4 동작을 유지한다. 단순히 텍스트 파일만 추가하지 않고 실행 루프, 하네스, 브라우저 워커와 보고까지 J2.5를 명시적으로 연결한다.
- 기존 `CommandRuntime`, `BrowserHTTP`, `web_discovery`, 실행 로그와 종료·복구 경로를 최대한 재사용한다. 기존 J2의 same-origin·리다이렉트 검사, 제한 시간, 중단·자원 정리, 실패와 부분 출력 보존을 유지한다. 대상이 반환한 내용은 지시가 아니라 신뢰할 수 없는 관찰 데이터다.
- v4.5에서 **실행별 안정 ID, 관찰의 출처와 시도 연결, 중복 대상의 병합, 최근 discovery 종류별 정보 보존**을 참고한다. v4.5 트리 전체, 별도 scorer와 추가 원격 모델은 도입하지 않는다.
- Ollama 로컬 모델을 주요 대상으로 한다. 기존 제공자 선택과 설정도 유지하되, 어느 제공자든 동일한 짧은 결정 계약과 예산을 사용한다.

## 조사 흐름

1. 사용자가 목표·대상·모델·기존 예산을 지정하고 J2.5를 선택한다. 현재 실행 전용 상태를 만들며 이전 실행 기록을 자동으로 가져오지 않는다.
2. 코드는 대상 시작 URL을 관찰하고 렌더링된 페이지와 이미 확보한 텍스트에서 입력·같은 origin의 이동 단서·스크립트 선언을 추출한다. 선언, 실제 접근 및 텍스트 분석은 각각 기록한다. 접근 실패와 잘림도 관찰로 남긴다.
3. 코드는 중복된 페이지·스크립트·입력 참조를 합치고 실행 중 안정적인 ID를 부여한다. 모델에 목표, 최근 관찰, 미완료 항목, 출처와 남은 예산을 작은 구조화 요약으로 전달한다. 길이 제한에 걸리면 종류별 최신 항목을 우선 남기고 생략 수·원본 참조를 표시한다.
4. 모델은 허용된 행동 하나, 기존 참조 ID, 짧은 판단 근거를 JSON으로 반환한다. 입력 비교를 고르면 해당 입력의 가설과 정상값·시험값도 제안한다. 모델이 URL, 코드, 셸 명령이나 파일 경로를 새로 만들어 실행할 수 없다.
5. 코드는 결정의 형태와 참조를 검증한 후 고정된 동작을 실행한다. 결과와 실패를 원래 참조·실행 단계에 연결하고 다시 모델에 전달한다. 허용되지 않거나 불가능한 결정은 실행하지 않고 사유를 반환한다.
6. 모델이 종료하거나 시간·호출·도구 예산이 끝나면 코드가 관찰, 비교, 실패, 남은 작업과 모델 주장을 구분한 보고를 만든다. 마지막 모델 호출 1회는 기존처럼 보고에 예약하되, 모델 보고가 실패해도 코드 보고를 보존한다.

시작 관찰과 각 페이지 관찰·스크립트 분석·입력 비교는 각각 도구 호출 1회를 사용하고 시간·중단 한도를 지킨다. 입력 비교의 최대 세 HTTP 요청은 하나의 도구 호출에 속하지만 실제 요청 횟수를 별도 기록하고 매 요청 전 시간·중단 여부를 확인한다. 모델 호출 예산이 1회면 초기 관찰 이후 예약된 보고 호출만 사용한다. 자동 관찰에 필요한 도구·시간 예산이 없거나 관찰이 실패하면 그 사유를 보고하고 성공한 정찰로 취급하지 않는다.

## 첫 버전의 고정 행동

| 행동 | 모델이 고르는 것 | 코드가 수행하는 것 |
| --- | --- | --- |
| 페이지 관찰 | 현재까지 방문했거나 같은 origin에서 발견한 링크의 페이지 ID | 브라우저로 이동해 렌더링된 내용과 보이는 입력을 수집하고 정적 선언을 분석한다. |
| 스크립트 분석 | 이미 선언된 같은 origin의 스크립트 ID | 기존 HTTP 도우미로 가져온 텍스트를 기존 분석기로 분석한다. 응답 오류·본문 잘림·분석 잘림을 따로 남긴다. |
| 입력 비교 | 실제 GET 요청이나 단일 입력 선언의 ID, 정상값, 시험값, 가설 | 입력 이름과 대상을 확인한 GET 요청을 정상→시험→정상 순서로 보내고 각 응답과 차이·실패를 기록한다. |
| 종료 | 종료 사유 | 남은 항목과 한계를 포함한 보고를 작성한다. |

시작 페이지 관찰은 코드가 수행한다. 이후 이동과 시험은 모델의 유효한 선택을 거친다. URL·메서드·입력 이름은 코드가 보유한 참조에서만 가져오며 매 실행 전에 원래 origin을 다시 검증한다. 입력값에는 길이 제한을 둔다. 비교는 동일한 기준 요청을 보존하고 선택한 필드만 바꿀 수 있을 때만 진행한다. 이미 알려진 다른 필드나 인증 맥락의 값이 필요한데 확보하지 못했다면 임의로 채우지 않고 미완료로 남긴다. 각 요청의 결과는 성공한 단계와 실패한 단계, 시도 횟수와 순서가 구분돼야 한다.

현재 `web_discovery`는 선언에서 GET 쿼리값을 지우며 `BrowserHTTP`의 요청 캡처도 GET은 저장하지 않는다. 따라서 J2.5는 브라우저가 실제 전송한 같은 origin GET 중 쿼리 입력이 있는 요청을 제한된 워커 메모리에 보존하고 ID를 발급한다. 모델·일반 로그에는 공개 경로와 입력 이름만 전달하며 원본 쿼리값·쿠키·인증 헤더는 넣지 않는다. 비교 시에만 보존된 요청과 현재 브라우저 인증 맥락을 사용하고 선택한 필드 외의 값과 중복 필드를 보존한다. 워커 재시작으로 요청이 만료되면 재수집을 요청하고 예전 ID를 실행하지 않는다. 보존 개수 초과·지원하지 않는 인코딩·모호한 중복 필드는 명시적으로 제한 또는 거절한다.

정적 선언만 있고 실제 GET이 관찰되지 않은 경우에도, 분석기가 원래 선언을 같은 origin의 단일 입력 GET으로 확인했다면 코드가 모델이 제안한 정상값으로 첫 기준 요청을 만들 수 있다. 이는 **선언을 바탕으로 한 시험**으로 표시하며 브라우저에서 실제 입력이 처리됐다고 주장하지 않는다. 다중 입력이나 필요한 원래 값이 불명확한 선언은 기준 요청 불명으로 남긴다. 어느 경우든 대상의 숨은 필수 입력이 없다는 것을 보장하지 않는다.

관찰된 `#/...` 또는 `/#/...` SPA 링크는 출처 페이지와 fragment를 함께 보존하고 같은 origin의 별도 페이지 참조로 열 수 있게 한다. 기존 분석기는 일부 fragment를 제거하므로 실제 관찰된 링크에서 이를 보존하도록 보완한다. fragment를 지워 서로 다른 화면을 합치지 않는다. 일반 버튼 클릭이나 자동 로그인처럼 링크만으로 재현되지 않는 이동은 첫 범위에서 미지원으로 남긴다.

이 첫 범위의 자동 비교는 GET으로 제한한다. POST 등 상태 변경 요청의 자동 비교, 로그인 절차, 파일 업로드, 여러 신원 사이의 비교와 임의 스크립트 실행이 필요한 경우에는 미지원·미완료로 기록한다. 브라우저 페이지 자체가 발생시키는 요청에는 기존 same-origin 정책이 적용되므로 POST가 발생할 수 있다. GET도 대상 구현에 따라 상태를 바꿀 수 있으므로 실제 실행은 사용자가 허가한 목표와 범위에서 이뤄진다. 기존 J2의 별도 사용 방식은 유지한다.

정적 선언은 실제 요청 처리의 증거가 아니다. 코드가 비교한 차이, 모델의 가설과 보안 영향 주장은 별도 필드로 기록하며 응답 차이나 성공 상태만으로 취약점을 확정하지 않는다.

## 결정·실행 계약과 실패

- 탐색 단계의 결정은 `action`, 기존 `ref`, 짧은 `reason`을 기본으로 하고 입력 비교에만 제한된 `hypothesis`, `normal`, `test`를 받는다. 이 단계에서 모델이 종료를 고르면 참조·시험값 없이 짧은 종료 사유를 받고 추가 보고 호출 없이 코드가 보고한다. 예산에 따라 마지막 예약 호출에 들어갔다면 별도의 보고 전용 스키마로 종료와 제한된 보고 본문을 받는다. 알 수 없는 필드·행동·ID, 유형이 다른 ID, 빈 값, 과도한 길이와 동일한 정상/시험값은 거절한다. 스키마 지원 모델에는 JSON 스키마를 전달하고, 응답은 제공자와 무관하게 실행 직전 다시 검증한다.
- 사이트 텍스트에 포함된 명령이나 모델이 조작한 식별자는 권한이 되지 않는다. 워커에는 검증된 유형과 데이터만 넘기고, 모델 값이나 사이트 문자열을 실행 코드·셸 문자열에 끼워 넣지 않는다.
- 형식 오류는 기존 모델 호출 예산과 마지막 보고 예약 안에서 제한적으로 수정 요청한다. 반복 실패·모델 연결 실패·시간 초과 시 자동으로 임의의 시험을 대신 고르지 않고 미완료 보고를 남긴다. 중단 중인 실행은 즉시 종료 경로로 간다.
- 세 번의 비교 중 실패하거나 취소되면 이미 받은 응답은 부분 결과로 보존하고, 비교 성공이나 보안 판정으로 바꾸지 않는다. 양쪽 정상 응답이 다르면 기준 응답이 불안정하다고 표시하고 시험값에 의한 차이로 단정하지 않는다. 상태·본문 해시 등 비교한 항목과 잘림 여부를 남긴다. 다른 입력으로의 자동 재시도는 하지 않는다.
- 코드가 확보한 관찰 ID, 모델 결정의 call ID, 실행 ID, 비교 단계, 출처와 원본 보존 위치를 연결한다. 토큰·호출·소요 시간, 각 실제 요청의 개수와 실패를 기록한다. 코드가 수행한 작업도 기존 도구 예산을 소비한다.

## 상태·맥락·보고

- 실행별 상태는 참조, 출처, 관찰, 비교 시도, 미완료 사유, 모델 주장과 생략 수를 담는다. 같은 입력이라도 서로 다른 메서드·인증 맥락을 합치지 않는다. URL의 쿼리값만 바뀐 시험은 별도 입력으로 중복 등록하지 않되 서로 다른 실제 기준 요청은 별도 참조로 남긴다. 원본 쿼리값은 워커 메모리에만 두고 영속 로그에는 공개 경로·필드 이름·요청 참조와 비교 결과만 보존한다.
- 모델 맥락은 현재 후보, 최근 실행 결과, 각 종류의 최근 discovery와 미완료·오류를 우선한다. 참조 ID와 출처는 축약 전후 동일해야 하며, 너무 작아 필수 맥락을 담을 수 없으면 명시적으로 종료한다.
- 최종 보고는 실행·관찰 사실, 모델이 제안한 가설, 실제 비교와 그 한계, 미실행·실패, 남은 작업을 구분한다. 모델이 `confirmed`라고 말해도 독립 검증 결과가 생기지는 않는다. 상태 및 기존 API에 `J2.5`가 식별되도록 저장하고, 기존 J2 기록의 읽기·보고와 충돌하지 않게 한다.

## 검증과 완료 기준

- 외부 사이트·실제 브라우저·실모델 없이 fake transport와 fake runtime으로 시작 관찰 → 입력 발견 → 모델의 선택 → 정상/시험/정상 비교 → 출처가 있는 미확정 보고의 전체 연결을 검증한다. 모델이 Python이나 셸 코드를 작성하지 않아도 이 흐름이 돌아야 한다.
- 관련 단위 테스트로 결정 스키마·존재하지 않는 ID·다른 origin·GET 원본의 보존과 마스킹·만료·단일 입력 선언과 다중 입력 제한·SPA fragment·잘린 데이터·부분 실패·중단·모델 형식 오류·보고 예약·기존 J2 동작·작은 컨텍스트에서의 최신 참조 보존을 확인한다. 사용자 승인 없는 화면 검증과 전체 테스트는 실행하지 않는다.
- 오프라인 고정 사례에서 J2와 J2.5가 같은 목표와 예산으로 받은 **모의** 결정을 재생하고 유효 결정 수, 첫 후보 비교까지의 단계, 실행·모델 실패, 호출 수를 각각 기록한다. 고정 사례 성과를 실모델의 취약점 발견율로 해석하지 않는다. 실제 성과 판단은 같은 대상 초기 상태·로컬 모델·예산으로 반복 실험하고 별도 근거를 확인해야 한다.

## 구현자가 정할 사항

작은 로컬 모델에서 안정적인 JSON 스키마의 구체적 필드 길이와 제한값, 상태 저장의 내부 자료구조, 기존 하네스의 공통 전송·로그 코드를 재사용하는 연결 방법은 구현 시 결정한다. 이 선택은 위 행동 범위, 예산, 출처 연결과 보안 경계를 바꾸지 않는다.
