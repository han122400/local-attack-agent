# J2.5 블랙박스 조사·검증·보고 설계

상태: 사용자가 혼합형 설계의 자율 진행을 요청했다. 50%는 예시이며, 발견 가능한 검증된 취약점을 최대한 많이 찾는 것이 목표다.

## 목적과 합의된 방향

사용자는 로컬 LLM이 판단하고 코드가 실행하는 J2.5를 유지하면서, 블랙박스 조사로 가능한 한 많은 취약점을 찾고 실제 공격으로 정보를 얻은 과정과 결과를 보고받고자 한다. 두 건 중 한 건 또는 50%는 비율의 예시이며 고정된 합격선이나 조사 중단 조건이 아니다. 사용자는 아래 세 대안 중 **혼합형**을 선택했다. 새 버전 이름을 만들지 않고 기존 `J2.5`를 발전시킨다.

1. **유형별 검증 모듈만 사용:** 실행과 결과를 통제하기 쉽지만 구현된 시나리오 밖의 흐름에 약하다.
2. **범용 브라우저 행동만 사용:** 유연하지만 작은 모델이 많은 단계를 조합해야 하므로 시간과 오류가 늘 수 있다.
3. **선택한 혼합형:** 자주 필요한 조사·검증은 코드 기반 모듈로 수행하고, 모듈이 맞지 않는 흐름은 범용의 제한된 브라우저·요청 행동으로 진행한다. 모델은 각 조사 단계에서 후보·가설·다음 행동을 선택한다. 코드는 실행, 한계 검사, 관찰, 증거 연결과 보고를 맡는다.

성능은 구현 이후 실험으로 입증해야 한다. 현 J2.5의 정상 검색값 비교, 실행 성공률, 모의 결정 재생, 단일 실험이나 모델의 자기 평가는 취약점 발견 성능의 근거가 아니다. 비율이 50%에 도달해도 조사 예산과 근거가 남아 있으면 더 많은 사례를 찾는다. 한 번의 대상 조사 결과를 보고하되, 성능 주장은 여러 대상 사례와 반복 실행의 분모·분자를 함께 보여준다.

## 현재 상태와 바뀌는 범위

- 현재 J2.5는 페이지·스크립트 관찰과 GET 정상→시험→정상 비교를 지원한다. POST 자동 비교, 로그인, 사용자별 권한 비교 및 일반 버튼 클릭은 없다. 응답 비교는 주로 상태·길이·본문 해시에 의존하고 독립적으로 검증된 취약점 수는 `null`이다.
- 기존 `CommandRuntime` 브라우저 워커, `BrowserHTTP`, `J25Actions`, `J25Runner`, `Harness`, 세션 로그·종료·복구, 프롬프트 선택, 스코어와 내보내기를 확장한다. J1·J2·v4의 동작과 기존 J2.5 기록의 열람을 보존한다.
- 개발 대상은 일반적인 웹 애플리케이션의 블랙박스 조사다. Juice Shop의 이름·힌트·정답 경로에 특화된 탐색 코드를 넣어 성능을 맞추지 않는다. 학습용 라벨과 검증기는 별도 평가 경계에서만 사용한다.
- 사용자가 허가한 대상과 테스트 신원 안에서만 실행하며, 기존 same-origin·리다이렉트 검사와 취소·시간·모델 호출·도구 호출 예산을 유지한다. GET도 상태를 바꿀 수 있다. 쓰기·삭제·외부 전송과 같은 영향은 자동으로 허용했다고 간주하지 않으며, 상태 변경 검증은 승인된 범위의 격리되었거나 복구 가능한 시험 데이터에서만 실행한다.
- 제품 기본 동작에 새 원격 모델·클라우드 전송·의존성 다운로드를 추가하지 않는다. 모델이 Python·셸·임의 실행 코드를 생성해 실행하지 않는다. 웹 페이지·응답·모델 설명은 신뢰할 수 없는 데이터다.

## 조사와 실행

1. 코드는 페이지, 링크·SPA 경로, 화면 입력, 같은 범위의 실제 요청과 응답, 세션 상태를 관찰하고 안정적인 참조 ID를 만든다. 선언과 실제 관찰, 요청·응답의 출처, 누락·만료를 구분한다.
2. 후보는 사용자 목표, 관찰된 기능·입력, 지원되는 검증 방식, 이미 수행한 행동과 근거를 바탕으로 우선순위를 매긴다. 한국어 두 글자 목표와 영어 경로처럼 표기가 다른 경우가 그대로 누락되지 않게 하되 순위는 확정 판정이 아니다. 후보 원본과 미검토 항목은 보존한다.
3. 모델은 현재 관찰과 선택 가능한 행동·참조를 보고 다음 가설·후보·시험을 짧은 구조화 응답으로 선택한다. 코드가 가능한 행동과 실제 표시된 참조로 스키마를 제한하고 실행 직전에 다시 검사한다. [Ollama의 JSON 스키마 출력](https://docs.ollama.com/capabilities/structured-outputs)은 이 계약을 전송할 수 있지만, 제공자 지원 여부와 관계없이 실행기 검증은 필수다. 이미 완료된 행동이나 동일 실패의 무한 반복, 없는 참조와 범위 밖 선택은 실행하지 않는다.
4. 유형별 모듈은 입력·요청의 기준 관찰, 허용된 시험과 대조·재확인을 코드로 수행하고, 각 요청·결과·실패를 개별 단계에 기록한다. 인증·세션과 사용자별 접근 차이, 입력 처리·인젝션, 브라우저 내 입력 처리, 정보 노출 및 설정 문제 등 여러 유형을 대상으로 한다. 일반적인 유형과 관찰에 기반해 확장하며 특정 실습 문제의 정답을 박아 넣지 않는다.
5. 모듈로 진행할 수 없는 경우에도 모델은 코드가 제공하는 탐색, 표시된 입력 조작과 제출, 관찰된 요청의 제한된 재현, 기준선과 결과 비교, 허가된 테스트 계정·세션 선택 같은 범용 행동을 사용할 수 있다. POST·폼·로그인과 신원 간 비교를 지원하되 대상·메서드·필드·세션·데이터 사용 권한을 실행기에서 검증한다. 코드가 한 단계 안에서 필요한 정상/시험/재확인을 수행할 수 있지만 다음 조사 단계는 모델이 판단한다.
6. 모델의 출력이 유효한 행동일 뿐 실제 성공이라는 뜻은 아니다. 코드가 부분 응답·타임아웃·불안정한 기준·오라클 부재·권한 부족을 구분해 모델에 돌려주고 실패 시에도 증거와 남은 작업을 보존한다. 외부 서비스나 추가 신원이 없으면 해당 한계를 명시한다.

## 성공 판정과 증거

- 한 건은 평가에서 사전 정의한 **서로 다른 취약점 사례**다. 같은 취약점에 대한 여러 후보·요청·재시도는 한 건으로 합치고, 시도 횟수와 반복 결과는 별도로 남긴다. 동일 페이지의 서로 다른 실제 원인·영향은 별도 사례가 될 수 있다.
- 사용자의 성공 조건은 발견한 취약점을 실제로 시험해 **그 공격으로 정보가 얻어진 것**이다. 정보는 실습용 가짜 값이나 검증용 표식처럼 민감하지 않아도 된다. 다만 정상적인 공개 페이지 조회, 단순 응답 차이, 상태 코드, 모델 주장만으로 취약점과 공격 성공을 만들지 않는다. 기준 동작, 시험, 결과를 연결하고 해당 유형에 맞는 독립적인 검증 근거를 요구한다.
- 증거에는 대상 버전과 범위, 신원·전제 조건, 발견 출처, 가설, 시험 순서와 입력의 안전한 표현, 기준선과 실제 관찰, 획득한 정보의 검증 가능한 안전한 표현, 실행 ID·시간·실패, 재확인 결과를 연결한다. 인증정보·쿠키·토큰·실제 개인정보는 모델 맥락과 일반 보고서에 넣지 않는다. 실습용 표식과 마스킹된 발췌·해시를 사용하고, 재현에 필요한 테스트 신원은 비밀값을 제외해 기록한다.
- 판정은 적어도 `후보`, `시도됨`, `정보 획득이 관찰됨`, `독립 검증됨`, `실패`, `미확인/부분`을 구별한다. 유형별 검증기가 보안 효과와 정보 획득을 독립적으로 확인할 수 없으면 모델이 확정이라고 해도 미검증으로 남긴다. 실습 오라클의 챌린지 완료만으로 실제 정보 획득까지 있었다고 가정하지 않는다.
- 일반 실제 대상에는 사전 정답이 없을 수 있다. 이때는 확보한 근거의 신뢰 수준과 검증된 건수·실패·미확인을 보고하고, 전체 실제 취약점 대비 비율은 **측정 불가**로 둔다. 0건을 분모로 100%라고 표시하지 않는다.

## 블랙박스 성능 평가

- 평가 담당자는 실행 전에 대상 버전, 고유한 정답 사례, 유형·난이도·필수 조건, 독립 판정법, 허용 범위와 제외 사유를 고정한다. 모델과 제품 실행기에는 정답 목록, 평가 오라클, 문제별 해결법이나 숨겨진 힌트를 주지 않는다. 실습 앱이 공개하는 챌린지 목록·힌트가 모델 입력이나 자동 모듈에 유입된 실행은 정답 오염으로 표시하고 엄격한 블랙박스 성능 점수에 넣지 않는다.
- 평가 오라클은 에이전트와 분리한다. Juice Shop의 챌린지 상태는 종료 결정 후 **초기화 전에** 별도 관찰자가 보존하고, 모델의 탐색 결정에는 전달하지 않는다. 제품의 관찰·대조 증거와 실습 오라클을 대조해 발견, 공격 실행 및 정보 획득을 확인한다. 오라클 획득 실패는 미확인으로 남기고 정리·초기화는 계속한다.
- 제안하는 검증 기본값은 사전에 등록한 실습·로컬의 고유 취약점 사례 **최소 20건**, 최소 4개 보안 유형과 서로 다른 난이도이며, 정상·비취약 대조 사례도 별도로 포함한다. 개발용과 최종 평가용 사례를 실행 전에 분리하고, 최종 평가에는 최소 10개의 고유 취약점 사례와 최소 3개 유형을 남긴다. 최종 평가에서 각 유형은 최소 두 건이고 한 유형이 절반을 넘지 않게 구성한다. 이는 신뢰할 만한 평가를 위한 설계 제안이지 사용자가 이미 승인한 숫자는 아니다.
- 평가 대상은 실제로 활성화돼 있고 허가된 범위와 설정된 전제 조건에서 실행 가능한 사전 등록 사례다. Docker에서 비활성인 항목, 외부 API가 없어 불가능한 항목 등은 이유·유형·개수를 명시해 별도 집계한다. 반대로 J2.5가 아직 지원하지 않거나 시도하지 못한 **활성·허용 사례는 분모에서 빼지 않고 미발견/미완료로 센다.** 제외 항목의 중복은 합산해 중복 제거한다.
- 현재 로컬 `juice-lab` v20.2.0의 읽기 전용 관찰에서는 116개 챌린지 중 18개에 Docker 제한이 표시되고 안전 설정은 `auto`였다. 각 실행의 실제 설정을 다시 확인하며, [Juice Shop 챌린지 문서](https://help.owasp-juice.shop/part1/challenges.html)가 설명하는 환경 제한과 일반 실습 태그를 정답 사례와 구분한다.
- 주 성과는 각 실행에서 `발견 + 실제 시험 + 정보 획득 + 독립 검증을 통과한 고유 사례 수 / 사전 등록된 활성·허용 고유 취약점 사례 수`다. 최종 평가 세트를 동일 조건에서 세 번 이상 새로 초기화해 실행하고 각 실행의 건수와 비율을 제시한다. 50%는 비교 가능한 예시로만 표시하며 합격선이나 중단 조건이 아니다. 분모가 0이면 측정 불가다. 같은 사례 반복 실행을 서로 독립된 취약점으로 부풀리지 않는다.
- 별도로 발견 후보 수, 검증된 건수, 후보 대비 검증 비율, 유형별 발견·검증 범위, 정상 대조에서의 오탐, 미시도·미확인, 환경 제외, 소요 시간, 요청·모델 호출과 재시도·토큰을 기록한다. 비율이 높더라도 한두 쉬운 사례만 보고 전체 성능이라고 주장하지 않는다.
- 현재 장비에 설치된 `qwen3:4b-instruct`, `qwen3:8b`, `Foundation-Sec-8B-Reasoning`은 비교 후보일 뿐 우승 모델로 미리 정하지 않는다. 동일한 대상 초기 상태·예산·평가 사례에서 모델별 지원 가능한 사고 모드와 단계별 짧은 프롬프트·맥락 설정을 비교한다. 출력 형식 유효성, 후보 선택·재현 가능 증거와 지연을 함께 보고, 하나의 모델·한 번의 실행이나 별도 일반 벤치마크 수치를 J2.5의 성능으로 일반화하지 않는다.

## 보고와 생명주기

- 사용자가 한 번의 조사 후 기존 화면과 내보내기에서 읽을 수 있는 보고서를 만든다. 요약에는 대상·범위·결과, 검증된 고유 건수, 사용 가능한 경우의 분모·분자, 유형·미검토 범위를 넣는다. 개별 항목에는 가설과 코드 관찰, 재현 순서·전제, 실제 얻은 정보의 안전한 증거, 대조·확인 결과, 실패·제한, 수정 방향을 분리한다. 재현·수정에 필요한 정보와 민감정보 마스킹은 [OWASP WSTG 보고 가이드](https://wstg.owasp.org/v4.2/5-Reporting/)를 참고한다.
- 모델 서술은 코드 증거와 구별하고 증거 없는 주장을 확정이나 안전성 입증으로 바꾸지 않는다. 모델 보고가 실패해도 구조화 실행 기록으로 부분 보고를 생성한다. 오래된 기록에 존재하지 않는 성공 건수나 50%를 추정하지 않는다.
- 진행 중 중단, 단계 실패, 모델 실패, 워커 재시작·참조 만료 또는 증거 수집 실패가 발생하면 가능한 부분 증거를 저장하고 남은 미확인 항목을 표시한다. 실습 오라클 스냅샷과 안전한 증거를 초기화 전에 보존하되, 스냅샷 실패가 런타임 정리와 초기화를 생략하게 하지 않는다. 정리나 초기화 실패는 기존 복구 상태로 남긴다.

## 완료 기준과 남는 선택

- 관련 자동 테스트는 타입·참조·범위 검증, 한국어 후보 정렬, 반복·예산·중단, 정상/오류·대조와 실패 부분 증거, 인증·세션 격리, 비밀 마스킹, 독립 판정·중복 제거, 오라클 격리·초기화 순서, 기존 버전 호환과 보고서 재현을 검증한다. 정상 사례나 응답 해시 변화만으로 성공하지 않는 부정 사례가 필요하다.
- 동일한 허가된 로컬 실습 환경에서 실제 브라우저·로컬 모델·평가 오라클을 사용해 위의 사전 등록 세트와 반복 기준을 실행한다. 범위·모델·예산상 실행하지 못했거나 근거가 부족하면 수치와 이유를 그대로 보고하고 목표를 완료로 표시하지 않는다. UI·전체 회귀 테스트는 프로젝트의 명시적 사용자 요청 규칙을 따른다.
- 기존 사용자 데이터와 미커밋 변경을 보존한다. 입력·상태 스키마의 구체적 구조, 모듈 구성과 테스트용 로컬 사례 구현은 위 요구를 지키는 범위에서 구현자가 정한다. 20건·4유형·최종 10건·3회라는 평가 규모는 승인된 출발점이며, 실제 제약이 생기면 숨기지 않고 범위와 근거를 기록한다.
